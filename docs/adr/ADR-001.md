# ADR-001: 采用 Spring Boot + MyBatis-Plus + Vue3 + SQLite 单体单机架构

## Status

Accepted

## Context

订单管理系统需在单机环境下部署运行，非功能约束为：约 50 并发在线、页面/查询/报表响应 ≤ 2s、约 20000 条业务数据、兼容 Chromium 系浏览器。系统为典型管理后台（RBAC + CRUD + 审核流 + 报表聚合），Phase 1 已交付 Vue3 Options API 原型（docs/prototype，plain JS stores，无 UI 框架）。需要确定后端框架、数据访问层、前端承接方式与数据库形态。

## Decision

采用单体架构：

- **后端**：Spring Boot + MyBatis-Plus，分层 Controller → Service → Mapper → SQLite。
- **数据库**：SQLite 单文件嵌入式数据库，表前缀 `tb_`，由 `sql/init.sql` 幂等初始化。
- **前端**：Vue 3 Options API + Vite + Vue Router 4，复用/改造 `docs/prototype/` 为正式前端，保留 plain JS store 模式；Phase 3 将 mock 数据替换为 REST API 调用。
- **部署**：单机 jar（后端）+ 静态资源（前端）同机部署。

## Consequences

### 正面

- SQLite 零运维、零独立服务进程，完全匹配单机部署 NFR；备份=拷贝单文件；2 万条数据在 50 并发下查询轻松满足 ≤ 2s。
- MyBatis-Plus `BaseMapper` 与条件构造器覆盖管理后台绝大多数 CRUD，样板代码少。
- 原型页面/路由/store 可直接延续，前端迁移成本低，无需引入 Pinia 或新 UI 框架。
- 单体部署链路短、排障简单，符合简单至上原则。

### 负面

- SQLite 写并发为单写者模型，不适合未来横向扩展为多实例高并发；若超出单机规模需迁移 MySQL/PostgreSQL。
- 单文件数据库无内建主从/高可用，需依赖文件级备份。
- 原型 Options API + plain store 在规模扩大后可维护性弱于 Composition API + Pinia，但当前体量下收益不明显，暂不重构。

## Alternatives considered

1. **MySQL/PostgreSQL**：更适合多实例与高并发，但要求独立数据库服务进程与运维（安装、账号、备份策略），与「单机部署、零运维」目标冲突；在 2 万条数据/50 并发下无必要，故拒绝。
2. **独立 SPA 全新工程（从零搭建 frontend/）**：可借机切换 Composition API/TS/Pinia，但会废弃已验收的 Phase 1 原型，重复实现 17 个页面与路由，交付风险与工期不可接受；选择复用/改造原型。
3. **JPA/Hibernate**：对象映射能力强，但对本项目的简单 CRUD 与条件查询场景偏重，且团队/原型技术延续性上 MyBatis-Plus 更贴近国内管理后台惯例，故选择 MyBatis-Plus。
